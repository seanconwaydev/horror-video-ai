# Image/video generation failure taxonomy — playbook

Last updated: 2026-09-02

A running log of real, observed oddities in generated previz images/video, and what (if anything) was done about each one. This is the raw material for eventually building a genuinely sustainable answer to "AI generation keeps producing small, specific oddities" — see the Methodology section for why a log, not just a growing pile of one-off prompt tweaks, is the point.

## Methodology

Sourced from Hamel Husain & Shreya Shankar's error-analysis process for evaluating LLM/generative systems ([LLM Evals: Everything You Need to Know](https://hamel.dev/blog/posts/evals-faq/)), the same methodology reportedly used inside teams at Anthropic and OpenAI — not invented for this project:

1. **Open coding** (where this doc lives right now): a human looks at a real output and writes a free-form note on what's wrong. This step can't be handed to an LLM — it requires actually knowing what a correct result looks like for this specific project. Every entry below is one open-coding note.
2. **Axial coding** (future, once there's enough volume): group the accumulated notes into a small taxonomy of ~5-10 recurring failure categories, rather than treating every note as its own permanent, isolated case. Husain's own guidance is to wait for **30-50 real traces** before this step is worth doing — clustering 6 entries would just be guessing at categories that don't have enough evidence yet.
3. **Golden eval set** (further out): once real categories exist, build a small fixed set of test scenes that get run whenever a prompt template changes, scored automatically (an LLM-as-judge — which `previz_review` already structurally is), to catch a regression before it costs a real image-generation run to discover.

Practically: **keep adding entries below as they're found, in the field's natural free-form-note style — don't force a rigid category onto the `tentative category` field either. It'll be revisited for real once there's enough here to cluster.**

### Per-genre rules — the plan, not yet the practice

Different kinds of scenes (a modern-day narrator, a pure historical reconstruction, something openly fantastical) plausibly need different rule sets — a phone-orientation rule is dead weight on a scene with no handheld device. The `genre` field below exists so that tagging happens from day one and doesn't need retrofitting later, but actually splitting rules by genre is real design work that needs real volume within each genre first — not attempted yet.

### Public benchmarks/guides — what's genuinely borrowable, and what isn't

There's no dataset, from Anthropic, OpenAI, or anyone else, of "historical-accuracy anachronism failures in AI video" — that's this project's own niche, and it has to be built from the entries below, not imported. What *does* exist publicly and is worth knowing about:

- **General text-to-image failure-mode benchmarks** — [T2I-CompBench](https://ar5iv.labs.arxiv.org/html/2307.06350) (6,000 prompts across attribute binding, spatial relationships, and complex compositions), [DrawBench](https://www.emergentmind.com/topics/t2i-compbench) (200 prompts testing counting/composition/conflicting/writing), [PartiPrompts](https://www.emergentmind.com/topics/t2i-compbench) (1,600 prompts), and [GenEval](https://www.emergentmind.com/topics/t2i-compbench) (object/attribute/position alignment). These are useful for the *vocabulary* of failure categories — e.g. T2I-CompBench's own "spatial relationships" category is literally the same class of bug as the phone-screen-orientation entry below — not for the historical-domain content itself.
- **Video-specific**: the [VBench](https://www.researchgate.net/publication/397699220_VBench_Comprehensive_and_Versatile_Benchmark_Suite_for_Video_Generative_Models) family evaluates dimensions including subject identity consistency, motion smoothness, temporal flickering, spatial relationship, physics, and commonsense — directly relevant vocabulary once video-generation-specific (not just previz-image) oddities start getting logged here.
- **OpenAI's own Sora 2 Prompting Guide** is already this project's primary sourced reference for prompt *structure* (see `docs/playbook/video-generation-prompting.md`) — first-party, genuinely reputable, and already informing this project's beat structure (subject/action/camera/lighting/style/audio).

None of the above have been applied to this project yet beyond the existing video-generation-prompting.md citations — noted here so they don't need re-discovering later, not because anything's been copied in.

## Log

Each entry: date, which run surfaced it, a tentative category (not yet a settled taxonomy — see Methodology), a genre tag, what was actually observed, and what (if anything) was done about it.

---

**2026-09-02** · Pompeii influencer run · *tentative category: retry-loop blindness to a structural (not random) rejection cause* · genre: modern-visitor-in-historical-setting
A Character's `face_build` field was hand-edited during scene-plan review to include "purple hair" (a scene_planning.py bug found separately: the field text is baked into every beat's prompt, ADR 0029's motivating case). previz_review correctly rejected it every time, but the automatic retry loop burned all 3 attempts blind before giving up, with no way to intervene mid-loop.
→ Addressed: [ADR 0029](../decisions/0029-on-rejection-edit-and-retry.md) (on-rejection edit/give-up hook, plus a same-concern-twice heuristic for `--yes` runs).

**2026-09-02** · Pompeii influencer run · *tentative category: staticness / insufficient motion across beats* · genre: modern-visitor-in-historical-setting
Across a full 12-beat run, the character stayed in the same standing position, orientation, and pose in nearly every beat — the only real variation was zoom level. The existing "vary camera framing" prompt rule wasn't enough on its own; framing changed, blocking didn't.
→ Addressed: scene_planning.py prompt rule requiring explicit body-position/pose variety per beat, not just camera framing (PR #23).

**2026-09-02** · Pompeii influencer run · *tentative category: attribute vagueness* · genre: modern-visitor-in-historical-setting
The character was meant to read as a modern-day visitor but came across ambiguous/not-clearly-modern — traced to vague wardrobe field text ("casual clothes" style phrasing) rather than concrete, specific clothing items.
→ Addressed: scene_planning.py prompt rule requiring specific, concrete, contemporary clothing items for out-of-era characters (PR #23).

**2026-09-02** · Pompeii influencer run · *tentative category: prop lighting realism* · genre: modern-visitor-in-historical-setting
A held smartphone rendered as an unrealistically bright, star-like light source. Traced to escalating "glow" language across beats' own `action`/`lighting` text ("a glowing smartphone" → "cool electric glow" → "phone-screen light"), not the Character's own description — nothing told the model to keep it subtle relative to the scene's real light source.
→ Addressed: scene_planning.py prompt rule requiring lit screens to be described as clearly weaker than the beat's main light source (PR #24).

**2026-09-02** · Pompeii influencer run · *tentative category: prop spatial/orientation consistency* (matches T2I-CompBench's own "spatial relationships" category) · genre: modern-visitor-in-historical-setting
A held phone's screen rendered facing the camera in a shot where the described geometry (over-the-shoulder from behind her) should have shown its back instead. Image models default to rendering a phone's iconic "screen-facing-viewer" view regardless of described camera geometry unless told the opposite outright.
→ Addressed: scene_planning.py prompt rule requiring an explicit "screen not visible to camera" statement whenever the described camera angle would naturally hide it (PR #24).

**2026-09-02** · Pompeii influencer run · *tentative category: review-scope / acknowledged-exception coverage* · genre: modern-visitor-in-historical-setting
A human acknowledged one specific anachronism (a time-travel smartphone) as intentional fiction. previz_review correctly followed that literal acknowledgment, but then separately rejected the character's modern *clothing* as an unacknowledged anachronism the moment a wider beat framing actually showed it clearly — even though "keep as intentional fiction" for a time-traveling visitor obviously implies her whole modern appearance, not just her phone.
→ Addressed (partially): [ADR 0030](../decisions/0030-acknowledged-fiction-covers-knock-on-consequences.md) broadened acknowledged_fiction to cover "natural knock-on consequences" of the acknowledged premise. **Recurred anyway** in the very next real run — see below.

**2026-09-02** · Pompeii influencer run (second real run) · *tentative category: review-scope / re-deriving pre-approved decisions* · genre: modern-visitor-in-historical-setting
ADR 0030's fix wasn't enough: previz_review rejected the same modern wardrobe again, with a logically fair argument this time — "a time traveler could plausibly have worn era-appropriate Roman dress... modern streetwear is not a natural consequence of the phone/time-travel fiction." True: owning a time-travel phone doesn't strictly *entail* modern clothes. The real problem was broader than acknowledged_fiction's scope: previz_review re-derives historical plausibility from scratch for *any* detail, including ones a human already approved at scene-plan-review time, not just the original premise-conflict text. Project owner's framing: "if the original prompt specifies that she's wearing modern clothes, that NEEDS to be unquestioned by every model that will check that info" — called this the single biggest problem in the project outside image generation itself.
→ Addressed: [ADR 0032](../decisions/0032-previz-review-trusts-planned-details.md) — previz_review now takes the actual Character/Beat objects and treats their scene-plan-approved details as settled, not re-derived. Third round on the same underlying issue (0026 → 0030 → 0032); the ADR notes that a fourth recurrence should prompt giving previz_review the whole ScenePlan by default instead of one more named exception.

**2026-09-02** · Pompeii influencer run (second real run) · *tentative category: image style consistency / photorealism fidelity* · genre: modern-visitor-in-historical-setting — **not yet addressed, open**
Generated images rendered as stylized 3D/CGI-doll rather than photorealistic, despite every beat's `style` field explicitly saying "photorealistic." Cleanly isolated by comparing reference images generated through the *identical* code path: the male character (plain older man, wool tunic) came out correctly photorealistic; the female character (young, modern colorful streetwear, "bright, expressive eyes" in her own description) came out stylized/cartoon. Location references were also correctly photorealistic. One beat rendered with the *entire scene* (not just the character) in a consistent cartoon style, and looked genuinely good in that style — camera/environment also seemed to vary more freely in that beat, raising an open question (owner's observation, unconfirmed) of whether the model is less anchored to the reference image when rendering in a non-photorealistic mode. Project owner's read: worth treating "the pipeline should support deliberate non-photorealistic styles, held consistently across a whole scene" as a real, first-class direction, not just a bug to stamp out — the actual requirement is *style consistency*, not *photorealism specifically*. No fix attempted yet; candidate next step is strengthening the character-sheet prompt's style line with an explicit negative constraint ("not 3D-rendered, not anime, not a game character"), matching the location prompt's already-more-specific style language.

**2026-09-02** · Pompeii influencer run (second real run) · *tentative category: pose/camera staticness, recurrence* · genre: modern-visitor-in-historical-setting — **not yet addressed, open**
Despite PR #23's pose-variety prompt rule, two accepted beats still looked nearly identical in positioning -- both closely matching the character reference image's own fixed pose. Working hypothesis (unconfirmed): the character reference image conditions too strongly, locking in pose (and possibly style, see the entry above) regardless of what the beat text describes. If true, this and the style-consistency entry above may share one root cause -- reference-conditioning dominance -- rather than being two separate problems.

**2026-09-02** · Pompeii influencer run (second real run) · *tentative category: compositional/role fidelity* · genre: modern-visitor-in-historical-setting
One rejected beat attempt showed the visiting time-traveler character apparently running the food counter herself, instead of the shop owner -- a plain compositional error (wrong character in the wrong role), not an anachronism. previz_review's anachronism-only framing had no way to catch this class of error at all.
→ Addressed: folded into [ADR 0032](../decisions/0032-previz-review-trusts-planned-details.md)'s scope widening -- previz_review's job now explicitly includes checking whether the image depicts the right character in the right role, not just whether anything is historically implausible.

**2026-09-02** · Pompeii influencer run (third real run, verifying ADR 0032) · *tentative category: character-reference identity fidelity* · genre: modern-visitor-in-historical-setting — **not yet addressed, open**
The secondary character's reference image was generated as an older woman (per her scene-plan description), but every beat image showing that character depicted an old man instead -- character-reference conditioning failed to carry gender/identity through to the beats for this character, even though the same mechanism worked correctly for the primary character across three separate runs now. Confirmed real (not a one-off): same run also re-confirmed the cartoon-vs-photorealistic style split from the previous run (the young female character's reference renders stylized/CGI; the older/secondary character's reference renders photorealistic) -- two independent runs landing on the same specific bias.

**2026-09-02** · Pompeii influencer run (third real run) · *tentative category: unprompted hallucinated detail in a reference image* · genre: modern-visitor-in-historical-setting — **not yet addressed, open, nuanced**
The influencer's character reference image included a literal coiled charging cable dangling from her hoodie pocket into the phone -- never mentioned anywhere in her text description. The image model hallucinated it, unprompted, directly into the *reference* image, which then leaked inconsistently into beats conditioned on it (one beat's first attempt was correctly rejected for it; an accepted beat elsewhere appears to still have it, unflagged). ADR 0029/0032's retry-and-review mechanism handled this specific case correctly, since the cable genuinely wasn't intended. Project owner's nuance, worth preserving: a charging cable tucked into a pocket is a *plausible, even desirable* deliberate detail for a modern-day character in some scenes -- the real gap isn't "eliminate hallucinated accessories," it's that there's currently no mechanism for a small, deliberate visual quirk on a character to be marked approved the way wardrobe now is (ADR 0032), so a genuinely intended detail like this would currently get fact-checked away by the same mechanism that correctly removed this unintended one. Expected to matter more as characters with more specific visual nuance (especially modern-in-past or past-in-modern characters) become more common -- not urgent now, flagged for when it comes up for real.

**2026-09-02** · Pompeii influencer run (third real run) · *tentative category: image legibility / staging, distinct from historical-plausibility* · genre: modern-visitor-in-historical-setting — **open, research-backed, not yet acted on**
Project owner's read on several accepted beats: individually plausible and often well-lit, but the actual intent/action reads as ambiguous or generic from the image alone -- hard to tell exactly what's happening or who's about to do what. Hypothesis (owner's, flagged as worth researching): this likely also hurts downstream video generation, since a keyframe/reference image with clearer staging and motion intent gives the video model more to work with. Confirmed by real research, not just intuition -- "staging" and "clarity of action" are established animation principles ("clarity beats complexity"), and real image-to-video papers (ConsistI2V, FrameInit, KeyVID) show a clearer keyframe/motion signal measurably improves video-generation output. Not yet turned into a concrete scene-planning/previz prompt rule.

**2026-09-02** · Pompeii influencer run (fifth real run, `--style photorealistic` after ADR 0033) · **verified fixed, phase 1**
All 4 beats accepted on the first attempt (zero rejections, vs. earlier runs' 2/4 and 4/4-with-retries), and both reference images plus all 4 beats held consistently, unmistakably photorealistic -- no drift anywhere. Pose/staging also visibly improved in the same run: beat 2 shows a genuine mid-stride turn with a real smile ("her frown melts into a broad smile"), beat 3 a clear two-character greeting with eye contact, beat 4 seated and gesturing over a full food spread -- each beat legibly different in pose, camera, and emotional beat, not just zoom level. The shopkeeper-identity mismatch also did not recur (reference and beats matched, both photorealistic). Can't yet attribute the improvement precisely to style-locking vs. the new staging/anticipation/secondary-action rules vs. both together, but the combination clearly worked on this run. Still only one data point -- phase 2 (`--style stylized`, checking whether the same consistency holds at the other end of the spectrum) not yet run.

**2026-09-02** · Pompeii influencer run (third real run) · *tentative category: style-consistency, needs a real mechanism* · genre: all — **in progress**
Confirms the earlier open style-consistency entry with more detail: within one run, different beats/references landed at different points on the realistic ↔ semi-realistic ↔ stylized spectrum, sometimes for the whole frame (an earlier run's beat 4) and sometimes for only the character while the environment stayed more photoreal (this run's beat 2). Project owner's framing: the pipeline needs to be able to *deliberately choose and hold* a point on this spectrum, not just avoid unintentional drift toward stylization -- both realistic and stylized are legitimate targets, the requirement is consistency once chosen.

Root cause, confirmed by inspection: style is currently specified independently in three separate places with no single source of truth -- `build_character_sheet_prompt`'s hardcoded style line, `build_location_reference_prompt`'s separately hardcoded style line, and every beat's own independently LLM-generated `style` field. Nothing forces these to agree with each other.

Real industry vocabulary for the spectrum, from research (not invented): Realistic / Semi-Realistic ("Pixar sorta-lifelike") / Stylized (cel-shaded, exaggerated, cartoon/anime) -- see [Character art style spectrum](https://prolificstudio.co/blog/stylized-vs-realistic/). Professional pipelines lock this via a "style bible" -- a document naming rendering approach, texture/detail level, and "what not to do" examples.

Two-phase plan, explicitly not to be collapsed into one step (the fuller phase must not be forgotten just because phase one ships first):
1. **Now**: a minimal `--style` CLI flag (photorealistic / semi-realistic / stylized) as the single authoritative style source, threaded into all three of the above call sites, replacing them. Verify it actually holds consistency on a real run before going further.
2. **Future goal, not yet started**: the fuller "style bible" -- a parameterized block (rendering technique, line-work, color grade, and which of the 12 animation principles like squash/stretch/exaggeration apply and how strongly, varying by realism level -- squash/stretch and exaggeration apply far more at the stylized end than the photorealistic end). This is the actual target; phase 1 is deliberately just the first step toward it, not a replacement for it.

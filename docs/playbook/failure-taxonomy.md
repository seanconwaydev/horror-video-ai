# Image/video generation failure taxonomy — playbook

Last updated: 2026-09-02

A running log of real, observed oddities in generated previz images/video, and what (if anything) was done about each one. This is the raw material for eventually building a genuinely sustainable answer to "AI generation keeps producing small, specific oddities" — see the Methodology section for why a log, not just a growing pile of one-off prompt tweaks, is the point.

## Methodology

Sourced from Hamel Husain & Shreya Shankar's error-analysis process for evaluating LLM/generative systems ([LLM Evals: Everything You Need to Know](https://hamel.dev/blog/posts/evals-faq/)), the same methodology reportedly used inside teams at Anthropic and OpenAI — not invented for this project:

1. **Open coding** (where this doc lives right now): a human looks at a real output and writes a free-form note on what's wrong. This step can't be handed to an LLM — it requires actually knowing what a correct result looks like for this specific project. Every entry below is one open-coding note.
2. **Axial coding** (future, once there's enough volume): group the accumulated notes into a small taxonomy of ~5-10 recurring failure categories, rather than treating every note as its own permanent, isolated case. Husain's own guidance is to wait for **30-50 real traces** before this step is worth doing — clustering 6 entries would just be guessing at categories that don't have enough evidence yet.
3. **Golden eval set** (further out): once real categories exist, build a small fixed set of test scenes that get run whenever a prompt template changes, scored automatically (an LLM-as-judge — which `previz_review` already structurally is), to catch a regression before it costs a real image-generation run to discover.

Practically: **keep adding entries below as they're found, in the field's natural free-form-note style — don't force a rigid category onto the `tentative category` field either. It'll be revisited for real once there's enough here to cluster.**

### Per-genre rules — the plan, not yet the practice

Different kinds of scenes (a modern-day narrator, a pure historical reconstruction, something openly fantastical) plausibly need different rule sets — a phone-orientation rule is dead weight on a scene with no handheld device. The `genre` field below exists so that tagging happens from day one and doesn't need retrofitting later, but actually splitting rules by genre is real design work that needs real volume within each genre first — not attempted yet.

### What counts as a successful outcome for horror specifically

Project owner's explicit framing (2026-09-14), worth preserving precisely so a future prompt-tightening pass doesn't accidentally engineer this back out: an unexplained, expectation-breaking visual detail is a **valid, even good** horror outcome, not a defect to eliminate just because it wasn't the literal thing asked for. Concrete case: a Wan-generated clip (see `video-generation-prompting.md`'s Replicate/Wan entry) showed an odd light spilling from a door in a way that wasn't obviously "horror-coded" by genre convention, but read as genuinely unsettling — "what... is that??" with no resolution — precisely because it was strange and unexplained. The same logic already applies to a scene simply not landing as scary and reading as funny instead (also explicitly called acceptable, even appreciated, by the owner). Practical consequence for future rule-writing in this doc and in `scene_planning.py`: don't treat every generation artifact or hallucinated detail in a horror scene as something to prompt-engineer away by default — check whether it actually breaks the scene before tightening a rule to prevent it, since over-constraining toward literal, on-the-nose scary imagery can make outcomes worse, not better, for this specific genre.

### Rule refinements are scenario-specific, not genre-wide, by default

A refinement made for one *kind* of horror scene (a domestic-interior haunting, this doc's main example so far) is not assumed to generalize to a structurally different one (an outdoor chase, a body-horror scene, a slasher scenario) just because both are tagged `--genre horror`. This is the same lesson already documented for moderation-risk patterns specifically (`video-generation-prompting.md`) generalized to rule-writing as a whole: expect each new *type* of horror scene to surface its own new staging/prompt lessons, log them here as they're found, and don't assume today's domestic-horror-tuned rules are load-bearing for tomorrow's different scenario. Whether horror sub-types eventually need their own routed rule variants (the way `composition_mode` already routes staged-vs-chaotic per ADR 0036) is a real open architectural question once enough scenario variety has actually been tried — not decided yet, tracked in `architecture.md`'s open questions.

### Editing a beat asked for all 8 fields when only a couple ever mattered

Real run (2026-09-15), same interactive session: editing a rejected beat's text meant being prompted through all 8 Beat fields one by one (including `location_id`, `duration_seconds`, `style` -- fields that essentially never need touching to fix a rendering mismatch, and which shouldn't change here without the revalidation decisions/0028 requires for a real structural edit). Project owner's read: "asking the human user to go through each field is far too much."
→ Addressed: beat edits (both the initial scene-plan review and the on-rejection retry loop) now prompt only for `action`/`camera`/`lighting` (`_BEAT_QUICK_EDIT_FIELDS`) -- the three fields that actually drive what gets rendered. Character/Location edits are unchanged (still every field), since the complaint was specifically about beats.

### The accept-override asked the same question twice; editing had no lightweight option

Real run (2026-09-15), same interactive session: two more real UX gaps surfaced immediately after the accept-override feature shipped. First, choosing `(a)ccept this image anyway` at the rejection prompt flowed straight into the same `(a)ccept/(r)eroll/(e)dit this beat?` confirm every normally-accepted image also goes through -- asking the same question again right after the human had just answered it. Second, `(e)dit` still meant rewriting a whole field even when only one small thing was wrong (project owner's example: beat 3 was "mostly acceptable, the girl in the photo is just FAR too large" -- rewriting the whole action to fix one proportion issue was overkill).
→ Addressed: an override-accept now skips the redundant second confirm entirely. A new `(f)eedback` choice at the rejection prompt takes a single short note and appends it to the beat's existing `action` text (not a rewrite) before retrying -- untested whether this specific appending approach reliably steers the image model (a size-correction note is a concrete, checkable instruction in the same vein as the occlusion-fraction language that worked elsewhere in this doc, but that's a reasoned bet, not a confirmed result yet).

### No way to keep a rejected image the human judges good enough

Real run (2026-09-15), project owner running interactively (no `--yes`) for the first time this session: hit a beat where `previz_review` rejected the first generated image, but the owner looked at it and judged it good enough to keep. The on-rejection prompt only offered keep-retrying, edit-and-retry, or give-up entirely -- no way to just accept the image the reviewer had rejected. The reviewer's verdict was structurally final; a human's own "good enough for me" judgment, which doesn't always match it, had no path to act on short of editing the beat and hoping for a different roll.
→ Addressed: `_generate_image_with_review`'s `on_rejected` callback now supports a third outcome, `"accept"`, which keeps that exact attempt's image as the final result instead of archiving it and regenerating. The interactive on-rejection prompt gained an `(a)ccept this image anyway` choice alongside keep-retrying/edit/give-up.

### Escalation arcs aren't reliably distributed across beats without an explicit rule

Real run (2026-09-15), same scene concept re-run verbatim through the real pipeline for comparison against an earlier run of the identical `--description`: a materially worse scene plan came out. The first run's scene-planning LLM call distributed the shadow's escalation across every beat (spikes feathering, a hooked neck, a hunched mass, then fully monstrous); this run's beats 1-5 never mentioned the shadow at all, and beats 6-7 both just echoed the root description's final "fully morphed" line verbatim with no progression between them. Same input, same flags -- genuine LLM run-to-run variance in how well an escalation described only in the root concept gets carried into every beat's own text. Nothing in `scene_planning.py` before this fix forced that distribution; it worked the first time somewhat by luck.

A second, related failure showed up in the same run: the two beats that did mention the shadow rendered with **no shadow at all**, not even a normal one ("only faint normal window-light shadows"), unlike earlier runs where the shadow at least appeared, just in the wrong shape. Traced to the `lighting` field: this run's beats described diffuse, multi-source ambient light ("faint blue moonlight... weak amber nightlight..."), where the earlier successful beats had explicitly named one single, hard-edged dominant light source ("the single low amber nightlight is the only source, throwing one long hard shadow"). A shadow this central to the scene appears to need an explicit single-light-source instruction to reliably render as a discernible silhouette at all, independent of whether its distortion is described correctly.

→ Addressed: `_THREAT_PRESENCE_RULE` (`scene_planning.py`) extended with two new requirements -- every beat must name its own explicit, distinct stage of a described escalation (not just the endpoints, and no two non-adjacent beats sharing a stage), and any beat where the threat is a shadow must specify one single, hard-edged dominant light source in its `lighting` field.

Separately, worth recording precisely (project owner's framing, 2026-09-15): the automatic retry loop's real value differs sharply by rejection category. Geometric/rendering defects (a limb clipping through furniture, a wall bending wrong) are worth blind regeneration -- closer to random noise a re-roll can fix. Whole-body pose/positioning mismatches against an exact plan (lying down vs. sitting, paused at the top of stairs vs. partway down) are often **not** worth it -- confirmed by inspection this run: `--yes`'s give-up heuristic (docs/decisions/0029) only catches a byte-identical repeated rejection reason, and all three of this run's pose-mismatch beats got reworded-but-identical rejections across all 3 attempts, burning every attempt on a pose the model was never going to hit. This matches that heuristic's own documented limitation ("a differently-worded critique of the same root cause slips past it") -- a real, now concretely-observed instance of it, not fixed as part of this session (the project owner is running future iterations interactively instead of via `--yes` for now, sidestepping it rather than fixing the heuristic itself).

### A distorted shadow needs open wall space, not a tight surface, to actually render

Real run (2026-09-14, "shadow gradually becomes monstrous across 7 beats" scene), later refined by two follow-up tests. First read (now superseded, kept for the trail): the image model handled both clean endpoints reliably -- a beat asking for a completely ordinary human shadow succeeded, and the final beat asking for a fully monstrous, horned, clawed shadow succeeded on the first attempt, genuinely striking. Three consecutive intermediate beats asking for a partially-transformed shadow (saw-toothed edges, a hooked overlong neck, a hunched non-human mass) each failed all 3 automatic attempts, reverting to an ordinary human silhouette every time. The original hypothesis was that a *partial/gradual* state is specifically harder than either endpoint.

Two follow-up tests (same day) point at a more specific, corrected explanation: **a shadow confined to a small area against nearby geometry (a closet door right beside the character's hand) defaults to an ordinary human silhouette no matter how explicit the distortion language is, while a shadow given a large, open wall/ceiling to spread across (the beat that succeeded) doesn't have this problem.** Two independent test images, generated from scratch (not edited from each other, ruling out reference-image anchoring as the cause) with identical "broad hunched mass, arms past the knees, claw-like points" language, both rendered as plain human silhouettes in the tight closet-door framing -- confirming this isn't about gradual-vs-endpoint distortion level at all, since even the full-endpoint description failed to render in this framing. It's specifically about how much open space the shadow has to occupy. No fix attempted yet; candidate next step is to always give a shadow that's meant to distort real open wall/ceiling space in its framing, rather than casting it onto a nearby confined surface, and to treat the earlier "partial states are hard" read as likely a symptom of this same framing issue rather than a separate root cause.

### Public benchmarks/guides — what's genuinely borrowable, and what isn't

There's no dataset, from Anthropic, OpenAI, or anyone else, of "historical-accuracy anachronism failures in AI video" — that's this project's own niche, and it has to be built from the entries below, not imported. What *does* exist publicly and is worth knowing about:

- **General text-to-image failure-mode benchmarks** — [T2I-CompBench](https://ar5iv.labs.arxiv.org/html/2307.06350) (6,000 prompts across attribute binding, spatial relationships, and complex compositions), [DrawBench](https://www.emergentmind.com/topics/t2i-compbench) (200 prompts testing counting/composition/conflicting/writing), [PartiPrompts](https://www.emergentmind.com/topics/t2i-compbench) (1,600 prompts), and [GenEval](https://www.emergentmind.com/topics/t2i-compbench) (object/attribute/position alignment). These are useful for the *vocabulary* of failure categories — e.g. T2I-CompBench's own "spatial relationships" category is literally the same class of bug as the phone-screen-orientation entry below — not for the historical-domain content itself.
- **Video-specific**: the [VBench](https://www.researchgate.net/publication/397699220_VBench_Comprehensive_and_Versatile_Benchmark_Suite_for_Video_Generative_Models) family evaluates dimensions including subject identity consistency, motion smoothness, temporal flickering, spatial relationship, physics, and commonsense — directly relevant vocabulary once video-generation-specific (not just previz-image) oddities start getting logged here.
- **OpenAI's own Sora 2 Prompting Guide** is already this project's primary sourced reference for prompt *structure* (see `docs/playbook/video-generation-prompting.md`) — first-party, genuinely reputable, and already informing this project's beat structure (subject/action/camera/lighting/style/audio).

None of the above have been applied to this project yet beyond the existing video-generation-prompting.md citations — noted here so they don't need re-discovering later, not because anything's been copied in.

**2026-09-02** · Pompeii influencer run (fifth real run, `--style photorealistic` after ADR 0033) · *tentative category: same-location beats read as visually repetitive despite different beat text* · genre: modern-visitor-in-historical-setting — **open, research-backed, not yet acted on**
Even with pose/staging clearly improved overall (see the run-5 entry above), the two beats sharing `pompeii_street` still looked like "the same background, a slightly different stance" rather than genuinely distinct shots -- project owner's read: acceptable narratively (a real short beat-to-beat progression), but too visually stiff, and likely to cause problems once these previz images become video-generation keyframes. Likely the same root cause as the pose-staticness entry directly above, but for the *location* reference and camera position specifically rather than character pose: a single flat location reference image, conditioned via `image_edit`, anchors toward its own fixed composition regardless of what a beat's `camera` field says.

Two research-backed levers, different sizes, neither implemented yet:
- **Cheap, available now**: professional shot planning's "coverage" concept -- a master shot establishes the space, additional shots come from genuinely different camera *positions* in it (not just a different angle adjective), deliberately varying subject-to-camera distance too. Candidate: a scene_planning.py rule requiring beats at a shared location to specify meaningfully different camera positions/distances, not just different framing language.
- **Bigger, for later**: the real technical fix sophisticated pipelines use for "same space, different camera position" is multi-ControlNet conditioning (depth map + camera pose controlled separately), not a single flat reference image -- ties back to this session's earlier ControlNet research on prompt-only spatial control's ceiling. A meaningfully bigger lift than the current single-reference-image approach, not a prompt tweak.

Owner's hunch, untested: stylized/non-photorealistic environments might tolerate more camera/composition variation from the same reference more easily than photorealistic ones (based on one earlier observation of a fully-cartoon beat deviating more freely). The upcoming `--style stylized` run is a natural, free check on this without a dedicated test.

Owner's explicit framing, worth preserving precisely: a genuinely static/unchanging shot could be a legitimate *deliberate* stylistic choice in some scenes -- the problem is specifically that it currently happens as an unintentional default, not something chosen. Mirrors the same philosophy already established for realism level (ADR 0033): both ends of a spectrum (static vs. dynamic camera, same as realistic vs. stylized) are legitimate targets, the requirement is that it's chosen, not drifted into. Seeing the same static background repeated is also flagged as a real immersion break for a human viewer, not just a technical nitpick -- raises the stakes on this one somewhat.

**2026-09-02** · Pompeii influencer run (third real run) · *tentative category: unprompted hallucinated detail in a reference image* · genre: modern-visitor-in-historical-setting — **not yet addressed, open, nuanced**
The influencer's character reference image included a literal coiled charging cable dangling from her hoodie pocket into the phone -- never mentioned anywhere in her text description. The image model hallucinated it, unprompted, directly into the *reference* image, which then leaked inconsistently into beats conditioned on it (one beat's first attempt was correctly rejected for it; an accepted beat elsewhere appears to still have it, unflagged). ADR 0029/0032's retry-and-review mechanism handled this specific case correctly, since the cable genuinely wasn't intended. **2026-09-02** · Pompeii influencer run (third real run) · *tentative category: image legibility / staging, distinct from historical-plausibility* · genre: modern-visitor-in-historical-setting — **open, research-backed, not yet acted on**
Project owner's read on several accepted beats: individually plausible and often well-lit, but the actual intent/action reads as ambiguous or generic from the image alone -- hard to tell exactly what's happening or who's about to do what. Hypothesis (owner's, flagged as worth researching): this likely also hurts downstream video generation, since a keyframe/reference image with clearer staging and motion intent gives the video model more to work with. Confirmed by real research, not just intuition -- "staging" and "clarity of action" are established animation principles ("clarity beats complexity"), and real image-to-video papers (ConsistI2V, FrameInit, KeyVID) show a clearer keyframe/motion signal measurably improves video-generation output. Not yet turned into a concrete scene-planning/previz prompt rule.

**2026-09-02** · Pompeii influencer run (fifth real run, `--style photorealistic` after ADR 0033) · **verified fixed, phase 1**

**2026-09-02** · Pompeii influencer run (third real run) · *tentative category: style-consistency, needs a real mechanism* · genre: all — **in progress**
Confirms the earlier open style-consistency entry with more detail: within one run, different beats/references landed at different points on the realistic ↔ semi-realistic ↔ stylized spectrum, sometimes for the whole frame (an earlier run's beat 4) and sometimes for only the character while the environment stayed more photoreal (this run's beat 2). Project owner's framing: the pipeline needs to be able to *deliberately choose and hold* a point on this spectrum, not just avoid unintentional drift toward stylization -- both realistic and stylized are legitimate targets, the requirement is consistency once chosen.

Root cause, confirmed by inspection: style is currently specified independently in three separate places with no single source of truth -- `build_character_sheet_prompt`'s hardcoded style line, `build_location_reference_prompt`'s separately hardcoded style line, and every beat's own independently LLM-generated `style` field. Nothing forces these to agree with each other.

Real industry vocabulary for the spectrum, from research (not invented): Realistic / Semi-Realistic ("Pixar sorta-lifelike") / Stylized (cel-shaded, exaggerated, cartoon/anime) -- see [Character art style spectrum](https://prolificstudio.co/blog/stylized-vs-realistic/). Professional pipelines lock this via a "style bible" -- a document naming rendering approach, texture/detail level, and "what not to do" examples.

Two-phase plan, explicitly not to be collapsed into one step (the fuller phase must not be forgotten just because phase one ships first):
1. **Now, verified working on both ends of the spectrum**: a minimal `--style` CLI flag (photorealistic / semi-realistic / stylized) as the single authoritative style source, threaded into all three of the above call sites, replacing them (ADR 0033). Run 5 (`--style photorealistic`) held consistent across every reference and beat, zero drift, zero rejections. Run 6 (`--style stylized`) also held consistent -- both references and all three accepted beats cohesively illustrated, no drift into photoreal or mixed styles, even in a rejected attempt (style stayed locked; the rejection was for an unrelated reason). The single-authoritative-source fix generalizes across the spectrum, not just the default.
2. **Future goal, not yet started**: the fuller "style bible" -- a parameterized block (rendering technique, line-work, color grade, and which of the 12 animation principles like squash/stretch/exaggeration apply and how strongly, varying by realism level -- squash/stretch and exaggeration apply far more at the stylized end than the photorealistic end). This is the actual target; phase 1 is deliberately just the first step toward it, not a replacement for it.

**2026-09-02** · Pompeii influencer run (sixth real run, `--style stylized`) · *tentative category: limb/prop spatial interpenetration + character non-interaction* · genre: modern-visitor-in-historical-setting
Project owner's direct observation, confirmed on re-inspection: in the rejected beat 4 attempt, her leg visually merges into the stone counter she's seated at with no clear boundary; in the accepted beat 3, her feet show the same issue against the counter base, and separately, the two characters (her and the owner) read as independently posed rather than interacting -- his expression/gaze stays passive against her animated greeting gesture, no shared eye-line or reciprocal cue, giving a "copy-pasted together" impression rather than one integrated moment. Real, named research grounding, not unique to this project: "Merged Limbs" and "Merged Objects" are documented diffusion-model artifacts (2025 CHI research), including the exact pattern observed here -- furniture legs merging into each other, objects lacking clear separation from adjacent elements, increasing in frequency at higher resolution. See [Characterizing Photorealism and Artifacts in Diffusion Model-Generated Images](https://ar5iv.labs.arxiv.org/html/2502.11989).
→ Addressed (partially, cheap mitigation only): scene_planning.py prompt rule requiring beats to describe the specific point of contact between a character and nearby furniture explicitly, and requiring characters in a shared beat to have a specific reaction to each other rather than an implicit shared frame. Not addressed: whether previz_review's scope should widen a third time to catch rendering-artifact-level defects like this, distinct from anachronism-checking (0026/0030) and plan-fidelity-checking (0032) -- flagged as an open scope question, not decided.

**2026-09-14** · First real horror-genre test run (`--genre horror --style stylized`, 4-beat single-location) · *tentative category: threat/antagonist absent from most beats' prompts* · genre: horror — **addressed**

**2026-09-14** · Second real horror-genre test run (same rule, 5-beat multi-room scene) · *tentative category: "monster reveal" framing overrides literal occlusion instructions* · genre: horror — **open, real limitation found**
The threat-presence rule worked as intended for beats where the threat stayed an environmental trace (a shadow line under a door, a shape at a frame edge) -- those beats accepted on the first or second try. But the one beat that framed the threat itself as the shot's subject (a humanoid shadow figure standing in a doorway, explicitly constrained to "one-eighth of the frame, occluded by the doorjamb, only a shoulder/head edge visible") failed all 3 automatic attempts: every attempt rendered a full, clearly-visible, roughly-centered silhouette instead, one attempt even hallucinating glowing eyes. `previz_review` correctly caught the mismatch every time -- this is a real image-generation bias (an "iconic monster reveal" composition winning out over an explicit occlusion constraint), the same shape as the already-logged phone-screen-facing-camera bias, not a review-gate gap. A separate, unrelated beat in the same run (a two-handed banister grip) also failed all 3 attempts for a generic pose-fidelity reason, nothing to do with the threat rule.
Project owner's read, worth preserving: the original creative premise was "the monster is always just out of sight" -- so a beat that stages the monster as a doorway reveal may simply be the wrong kind of beat to write for this premise, not a prompt-wording problem to keep fighting. The beats that stuck to pure environmental traces (never framing the threat as the shot's subject) succeeded without a fight and arguably serve the "never fully seen" premise better anyway. No fix attempted yet beyond the threat-presence rule itself; candidate next step, if this recurs, is a rule against ever framing the threat as a beat's explicit subject, restricting it to environmental-trace beats only.

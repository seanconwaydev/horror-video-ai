# Genre-conditioned pipeline design — playbook

Last updated: 2026-09-03

The project owner asked for real research (not guesswork) on three specific questions raised by a live conflict in `scene_planning.py`: a "staging" rule (clarity, one legible focal point) was fighting a surreal/absurdist genre's actual needs (asymmetric, chaotic composition), patched inline with prose hedges. The three questions: where/when should rules apply per-genre systemically; should genre be decided even earlier/more bindingly than the current `--genre` CLI flag; and should the pipeline split by genre entirely. This doc is the detailed research; [decisions/0036](../decisions/0036-genre-resolves-to-early-routing-signals.md) is the resulting decision.

## Controllable/genre-conditioned generation (academic)

Pipelines that condition generation on a category attribute do it by modifying specific pipeline *modules* based on that attribute, not by writing one universal instruction set with inline exceptions. "Style-Guided Planning" research specifically conditions the *planning/outline* step on the target style before content generation happens, rather than letting style leak in as a late modifier — directly relevant since this project's own planning stage (`scene_planning.py`) is exactly where the conflict showed up.

## Mixture-of-Prompts / Mixture-of-Experts

When categories are natural and discrete, the established pattern is: route the input to a category, then apply the specialist prompt/rule-set for that category, rather than write one universal prompt with per-category exceptions baked in ("a simplifying constraint on the router maps the input to one of M categories and subsequently routes it to one of the experts for that category" — a divide-and-conquer approach specifically chosen to avoid a single prompt trying to cover every case). This is a direct argument against the prose-hedge approach (a rule with an inline "unless genre says X" carve-out) and for named, selected rule groups instead.

## Screenwriting craft

Genre is the first, most decisive decision in professional screenwriting practice — made before plot, before character — and it's structurally binding, not just a flavor layered on afterward: "defining the genre before you start writing shapes every decision you'll make." This supports deciding genre early and bindingly, which this project's CLI already does (genre is the first flag).

**A sharper distinction matters here too**: Blake Snyder's *Save the Cat* genre taxonomy explicitly separates conventional genre labels (horror/comedy/thriller — these describe *tone*) from Save the Cat's own ten structural genres (Monster in the House, Golden Fleece, etc. — these describe *what mechanically drives the plot*, each with its own real beat-structure requirements). This project's single free-text `--genre` field currently does both jobs at once — a value like "surreal photo collage" is a tone/mode description, not a plot-structure category — and that conflation is part of why one rule (staging) can't cleanly apply or not apply based on genre text alone.

## Software architecture precedent

The Strategy pattern (a.k.a. Policy pattern), the Rules Engine pattern, and the Specification pattern are all established, named solutions to the exact anti-pattern this project's staging-rule prose hedge represents: conditional business rules scattered as inline exceptions inside otherwise-monolithic logic. The fix in all three is the same shape — externalize rule selection into a structured, swappable mechanism, keyed by an explicit condition, rather than growing one function's prose/branches indefinitely. "By extracting chaotic conditional business rules out of your core services and encapsulating them into interchangeable, modular strategies, you build a system designed for change."

## Content-moderation policy engines (real production precedent)

Content moderation is a mature, real production example of "different rules apply to different categories of the same kind of input," at scale. The established practice: route content to a category, then apply that category's policy/threshold set, with the *policy layer kept separate from the core detection logic* specifically so rules can be edited without retraining or touching the underlying system — "keeping policy out of the model lets teams iterate on rules without retraining." Directly analogous to this project's rule text needing to live in a structured, category-keyed form rather than hardcoded inline prose.

## LLM routing / intent-classification best practice

Production LLM systems that need per-category behavior classify **once, early, cheaply**, then have every downstream stage consume that already-resolved classification — they do not re-derive the category independently at every stage. Rule-based classification (not a full model call) is the recommended *starting point* specifically because it's simple, fast, and debuggable; fancier semantic/predictive routing is reached for only once a rule-based approach demonstrably falls short. This project's `requires_grounding` boolean (`decisions/0034`, `0035`) already follows this pattern correctly — resolved once, early, threaded through explicitly. The gap is that raw `genre`/`tone` free text is *not* resolved the same way: it flows into `scene_planning.py`'s prompt as raw text, re-interpreted by the LLM call each time, with no stable signal other stages (or other rules within the same stage) can share or trust — the actual mechanism behind the staging-rule conflict, and a case of the exact anti-pattern this research area warns against.

## Counter-perspective (considered, not followed here)

A game-design source argues genre conventions become a creative trap when treated as a priori rules rather than diagnosed post-hoc from a specific target experience — real, and worth naming, but judged not to apply to this project: game design's concern is about genre constraining *original creative vision*, whereas this project's problem is the opposite — genre-blind rules actively fighting a genre's *already-decided* creative intent (a real, observed defect, not a hypothetical constraint on invention). The reactive-only scoping below (build one named rule group at a time, only once a real conflict is observed) already absorbs the legitimate part of this caution — don't build a speculative genre taxonomy up front — without treating "genre" itself as suspect.

## Bottom line for this project

1. **Rule selection**: replace inline prose hedges with named, selected rule groups (Strategy/Rules-Engine pattern), built reactively — one group per rule, only once a real cross-genre conflict is actually observed, matching this project's existing preference for reactive rather than speculative resilience work.
2. **Early binding**: `--genre`/`--tone` stay free text (research and this project's own prior decision, `decisions/0035`, both support this — the flexibility is deliberate, not a gap). What's missing is a *derived*, small, closed-set classification — generalizing the pattern `requires_grounding` already uses correctly — computed once, early, and threaded through explicitly, instead of raw genre/tone text being independently re-interpreted per stage/rule.
3. **No pipeline split**: every relevant precedent (controllable-generation modules, MoE routing, content-moderation policy engines) treats category as a routing signal *within* one system, not a reason to fork the whole pipeline. A full split would replicate every future cross-cutting fix N times to solve a problem that, so far, is scoped to specific rules in specific stages.
